## Призначення

Цей документ зв’язує всі 23 критерії готовності зі специфікацією, вертикальною фічею, реалізованим API-контрактом, обов’язковими станами інтерфейсу та автоматизованими й браузерними доказами.

Матриця є індексом, а не заміною детальних task packets, ADR, OpenAPI-схеми або тест-кейсів. Стан `verified` означає, що реалізація має посилання на код, зелені автоматизовані докази та пройшла фінальний TP-904 release gate.

## Правила трасування

- ID `AC-01`—`AC-23` стабільні та відповідають нумерації розділу 21 специфікації.
- Пріоритет джерел: `SPECIFICATION.md` → погоджені ADR → прототип → демонстраційний JavaScript.
- Назви API нижче є цільовими operation/route contracts для подальшої фіксації в OpenAPI; вони ще не означають наявність endpoint у коді.
- Усі mutation-відповіді використовують спільний error envelope: `code`, `message`, `fields`, `correlation_id`.
- `401` означає відсутню/прострочену сесію, `403` — заборонену роль або scope, `404` може приховувати існування чужого об’єкта, `409` — конфлікт стану або конкурентної зміни, `422` — помилку полів.
- Гроші передаються цілим числом у копійках; час — ISO 8601 з UTC на API та `Europe/Kyiv` у UI.
- Критичні повторювані mutation (`finish_visit`, оплата, повернення, складська операція) мають ідемпотентний ключ.
- Для кожного рольового критерію потрібні позитивний тест дозволеної ролі та негативні тести заборонених ролей.
- Primary implementation ownership для кожного AC зафіксовано у [реєстрі вертикальних task packets](../planning/task-packets.md#5-покриття-acceptance-criteria).

## Обов’язкові gate-артефакти

Для переведення будь-якого рядка з `planned` у `implemented` потрібно додати:

1. посилання на task packet і, якщо потрібно, погоджений ADR;
2. OpenAPI operation та приклади success/error;
3. backend unit/integration тести, включно з negative RBAC;
4. frontend component test для validation/state logic;
5. Playwright-сценарій для user-visible acceptance criterion;
6. посилання на реалізацію audit event для mutation;
7. докази desktop/tablet/phone для користувацького екрана;
8. результат Docker test profile у CI.

Стани рядка:

- `planned` — джерело, цільовий контракт і докази визначені, реалізації ще немає;
- `in_progress` — є task packet і активна реалізація;
- `implemented` — код і локальні тести готові;
- `verified` — інтеграційний gate і пов’язаний acceptance test пройдені;
- `blocked` — потрібне рішення ADR або зовнішня залежність; причина має бути в останній колонці.
