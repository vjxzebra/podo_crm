# TP-1013 — PDF-квитанція та бланк рекомендацій

Статус: `done`
Дата: 2026-07-30

## Мета

Після проведення повної оплати reception або administrator може одразу
завантажити чи надрукувати один чорно-білий A4 PDF:

1. квитанцію з незмінними даними оплати, прийому та послуг;
2. окремий бланк із рекомендаціями подолога.

## API

`GET /api/v1/payments/{payment_id}/receipt?disposition=attachment|inline`

- доступ: лише ролі з finance access (`ADMIN`, `RECEPTION`);
- `attachment` використовується для завантаження, `inline` — для друку;
- endpoint явно підтримує `Accept: application/pdf`; JSON renderer збережений
  для стандартних API-помилок;
- відповідь має `application/pdf`, server-derived filename,
  `Cache-Control: private, no-store` і `X-Content-Type-Options: nosniff`;
- чужий або недоступний об'єкт не розкривається поза чинним finance scope;
- endpoint не створює нової фінансової операції та не змінює ledger.

## Джерела даних

Перша сторінка використовує immutable snapshots із `Payment`:

- номер і час операції;
- пацієнт, телефон, прийом, спеціаліст і касир;
- snapshot рядків послуг, кількості, ціни та суми;
- спосіб оплати, коментар і загальна сума;
- стан повернення, якщо воно вже проведене.

Друга сторінка використовує актуальні `VisitRecommendation` цього прийому.
Назва, контакти та optional logo беруться з поточного clinic profile. Якщо
object storage із логотипом тимчасово недоступний, квитанція все одно
генерується без логотипу.

## Формат документа

- рівно дві сторінки A4;
- чорно-білий друк, Unicode-шрифт із підтримкою української;
- сторінка 1: `КВИТАНЦІЯ ПРО ОПЛАТУ`, реквізити, таблиця послуг, спосіб і
  підсумок;
- сторінка 2: `БЛАНК РЕКОМЕНДАЦІЙ`, дані пацієнта/прийому, рекомендації та
  місця для підписів;
- complaint, examination notes, фото й інші clinical fields у документ не
  потрапляють.

## Фіскальна межа

Документ явно позначений `НЕ Є ФІСКАЛЬНИМ ЧЕКОМ`. Він є клієнтською
квитанцією/бланком рекомендацій CRM і не замінює розрахунковий документ,
сформований зареєстрованим РРО/ПРРО. Інтеграція з РРО/ПРРО, фіскальний номер,
QR-код і передавання розрахункових даних до ДПС не входять у TP-1013.

## UI

- після успішної оплати відкривається dialog із діями
  `Завантажити PDF` і `Відкрити для друку`;
- ті самі дії доступні з деталей уже проведеної оплати або повернення;
- завантаження використовує server filename;
- дія друку відкриває `inline` PDF у новій вкладці стандартного PDF-переглядача
  браузера, звідки користувач запускає системний друк;
- на широкому екрані PDF-дії не переносять текст усередині кнопок; на вузькому
  екрані дії складаються у вертикальний список;
- loading/error/retry стани не закривають фінансовий контекст користувача.

## Перевірки

- генерація двох A4-сторінок і коректне вилучення українського тексту;
- content, refund, recommendation, logo-storage fallback і відсутність
  clinical notes;
- auth/RBAC, `disposition`, OpenAPI snapshot і TypeScript client;
- UI після payment success, detail actions, download та print flow;
- візуальний Poppler render обох сторінок без обрізання.
